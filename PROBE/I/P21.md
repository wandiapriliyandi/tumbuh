# P21 — Bagaimana Repository V2 Menentukan Source of Truth ketika Satu Informasi Muncul di Banyak Artefak?

## Tujuan

Menetapkan prinsip **source of truth** pada repository V2 agar ketika informasi yang sama muncul pada Probe, README, index, metadata, atau derived view, tidak terjadi konflik mengenai artefak mana yang menjadi rujukan utama.

---

## 1. Titik Berangkat

P14 menetapkan bahwa index adalah navigation layer, bukan duplikasi isi.

P15 membedakan source dari derived view.

P20 membedakan cross-reference semantik dari navigation link.

Dari sini muncul persoalan yang lebih mendasar:

> **Jika satu informasi muncul di beberapa tempat, mana yang menjadi sumber kebenaran?**

Tanpa aturan ini, repository dapat memiliki beberapa versi informasi yang terlihat sama tetapi berbeda isinya.

---

## 2. Duplikasi Informasi Bukan Selalu Salah

Repository memang membutuhkan beberapa bentuk representasi.

Contoh:

```text
Probe
↓
Index
↓
README
↓
Graph / generated view
```

Masalahnya bukan semata-mata adanya pengulangan.

Masalah muncul ketika pengulangan tersebut menjadi **independent source** yang dapat berbeda tanpa diketahui mana yang benar.

---

## 3. Source of Truth

Source of truth adalah artefak yang memiliki otoritas utama untuk informasi tertentu.

Dengan kata lain:

> **Jika dua representasi berbeda, artefak mana yang harus dijadikan acuan untuk menyelesaikan konflik?**

Pertanyaan ini harus dijawab berdasarkan **jenis informasi**, bukan dengan menunjuk satu file sebagai sumber untuk seluruh repository.

---

## 4. Tidak Ada Satu Source of Truth untuk Semua Hal

Ini prinsip penting.

Tidak tepat mengatakan:

```text
README = source of truth untuk semuanya
```

atau:

```text
Git = source of truth untuk semua semantic meaning
```

Setiap jenis informasi dapat memiliki source yang berbeda.

---

## 5. Probe sebagai Source untuk Inquiry

Untuk isi inquiry:

```text
Question
Analysis
Finding
Decision
Boundary
Next Question
```

maka dokumen Probe adalah source utama.

Contoh:

```text
P21.md
```

menjadi source untuk isi inquiry P21.

Index tidak boleh menggantikan isi tersebut.

---

## 6. Metadata Probe sebagai Source untuk Metadata

Jika metadata seperti:

```text
P-number
Lifecycle
Decision
Relations
```

didefinisikan dalam dokumen Probe, metadata tersebut menjadi source untuk informasi metadata Probe.

Index hanya merepresentasikan metadata tersebut untuk navigasi.

---

## 7. Index sebagai Derived View

P14–P15 menetapkan index sebagai navigation layer.

Maka:

```text
Probe metadata
      ↓
   generator
      ↓
    Index
```

Jika index berbeda dari Probe:

```text
Probe = source
Index = stale / derived artifact
```

Bukan sebaliknya.

---

## 8. README sebagai Repository Contract

README memiliki fungsi berbeda.

README dapat menjadi source untuk:

- tujuan namespace;
- aturan penggunaan;
- orientasi repository;
- convention;
- batas scope;
- contract dokumentasi.

Namun README tidak menjadi source utama untuk isi setiap Probe.

---

## 9. Git sebagai Historical Source

Git memiliki otoritas khusus untuk sejarah perubahan repository.

Git dapat menjawab:

```text
Apa yang berubah?
Kapan berubah?
Commit mana yang membuat perubahan?
```

Tetapi Git tidak otomatis menjawab:

```text
Mengapa sebuah relation secara semantik berarti DERIVED_FROM?
```

Untuk semantic meaning, repository documentation tetap diperlukan.

---

## 10. Schema sebagai Source untuk Aturan Metadata

Jika schema metadata didokumentasikan secara eksplisit, maka schema menjadi source untuk:

```text
field yang valid
format
required / optional
vocabulary
constraint
```

Probe menggunakan schema tersebut.

Index tidak boleh diam-diam mendefinisikan schema sendiri.

---

## 11. Governance Document sebagai Source untuk Aturan Governance

Aturan seperti:

```text
kapan P baru dibuat
bagaimana numbering dikelola
bagaimana lifecycle diperlakukan
```

harus memiliki sumber governance yang jelas.

P9 misalnya membahas governance P0–Pn.

Tidak seharusnya aturan governance hanya muncul sebagai catatan samping dalam index.

---

## 12. Source dan Derived View

Model utama P21:

```text
              SOURCE
                │
        ┌───────┼────────┐
        ↓       ↓        ↓
      Index   Graph    Summary
        │       │        │
        └───────┴────────┘
                ↓
          Derived Views
```

Source menyimpan informasi authoritative.

Derived view menyajikannya untuk kebutuhan tertentu.

---

## 13. Mengapa Derived View Tidak Boleh Menjadi Source Kedua?

Jika index diedit manual dan Probe juga diedit manual:

```text
P21.md → Decision: PASS
Index  → Decision: REVISE
```

repository sekarang memiliki dua klaim.

Governance menjadi tidak jelas:

```text
mana yang benar?
```

Karena itu derived view sebaiknya tidak menjadi independent semantic authority.

---

## 14. Single Source of Truth Per Concern

P21 menetapkan prinsip:

> **Satu concern harus memiliki satu authoritative source dalam scope yang jelas.**

Contoh:

| Concern | Authoritative source |
|---|---|
| Isi inquiry P21 | `P21.md` |
| Metadata Probe | Probe metadata sesuai schema |
| Repository rules | README / governance document terkait |
| Schema rules | Schema definition |
| Navigation summary | Index sebagai derived view |
| Historical change | Git history |

Tabel ini bersifat konseptual; format final repository belum ditetapkan.

---

## 15. Conflict Resolution

Jika dua artefak berbeda, langkah pertama bukan memilih berdasarkan siapa yang terakhir diedit.

Gunakan:

```text
1. Identifikasi concern
2. Tentukan authoritative source
3. Periksa revision/history
4. Perbaiki derived artifact jika stale
5. Jika source sendiri ambigu → human review
```

---

## 16. Last Modified Bukan Source of Truth

Artefak yang paling baru diedit belum tentu authoritative.

Contoh:

```text
README diedit hari ini
P21.md diedit kemarin
```

Tidak berarti README lebih benar untuk isi P21.

Authority ditentukan oleh **fungsi artefak**, bukan timestamp semata.

---

## 17. Copy-Paste Meningkatkan Risiko Drift

Jika isi Probe disalin penuh ke README:

```text
P21.md
↓ copy
README
```

maka perubahan pada P21 berpotensi tidak tercermin di README.

Jika ringkasan memang diperlukan, lebih aman membuatnya sebagai summary yang jelas statusnya sebagai derived representation.

---

## 18. Summary Boleh, Duplikasi Authority Jangan

Repository tetap boleh memiliki:

```text
short summary
index description
navigation text
```

Tetapi harus jelas bahwa summary tersebut bukan pengganti source.

Contoh:

```text
P21 — Source of Truth
Decision: PASS
```

di index adalah ringkasan.

Detail reasoning tetap berada di P21.

---

## 19. README dan Index Tidak Memiliki Fungsi yang Sama

### README

Berorientasi pada:

```text
purpose
rules
scope
orientation
```

### Index

Berorientasi pada:

```text
discovery
navigation
summary
```

Karena concern berbeda, source authority-nya juga berbeda.

---

## 20. Generated Artifact

Jika index dibuat otomatis:

```text
P*.md
↓
parser
↓
index
```

maka index adalah derived artifact.

Perubahan manual pada index sebaiknya tidak digunakan untuk memperbaiki semantic information yang sebenarnya berasal dari Probe.

Perbaikan dilakukan pada source lalu index dibangun ulang.

---

## 21. Manual Index pada Skala Kecil

Pada repository kecil, index manual masih mungkin.

Namun jika index manual dipelihara sebagai source kedua, risiko drift meningkat.

Maka prinsip yang lebih aman:

```text
manual index
→ acceptable for convenience

authoritative index
→ avoid when source already exists elsewhere
```

---

## 22. Source of Truth Tidak Berarti File Tidak Boleh Memiliki Referensi

Sebuah README dapat menyebut:

```text
P21
```

dan sebuah Probe dapat menyebut:

```text
P20
```

Referensi silang tidak menjadikan keduanya source untuk isi satu sama lain.

Reference ≠ authority.

---

## 23. Source of Truth dan Lineage

Lineage harus dapat dilacak dari authoritative identity.

Misalnya:

```text
P20
  ↓
FOLLOW_UP
  ↓
P21
```

Jika index hanya menampilkan:

```text
P20 → P21
```

index membantu navigasi, tetapi relation canonical tetap harus dapat ditemukan pada source Probe/metadata yang authoritative.

---

## 24. Source of Truth dan Archive

Ketika Probe diarsipkan, identity dan historical content tetap menjadi source untuk inquiry tersebut.

Archive tidak otomatis mengubahnya menjadi non-authoritative.

Yang berubah adalah lifecycle/context, bukan sejarah semantic inquiry.

---

## 25. Source of Truth dan Schema Migration

Jika schema berubah:

```text
Schema V1
↓
Schema V2
```

maka repository perlu mengetahui schema mana yang berlaku untuk artefak tertentu.

Migration tidak boleh membuat dua schema bersaing secara diam-diam.

Jika artefak lama masih menggunakan schema lama, status compatibility atau migration harus dapat ditentukan.

---

## 26. Source of Truth dan Repository Version

Repository version:

```text
v2.0.0
```

memberi context state repository.

Namun tidak otomatis menjadi source untuk isi semantic Probe.

Repository version adalah context/versioning layer, bukan semantic source.

---

## 27. Source of Truth dan Git

Git adalah historical record, tetapi repository content tetap menjadi semantic source sesuai concern-nya.

Contoh:

```text
Git:
P21 berubah pada commit X

P21.md:
isi terbaru P21
```

Keduanya saling melengkapi.

Tidak perlu menjadikan Git diff sebagai pengganti dokumen reasoning.

---

## 28. Human Review untuk Conflict Semantik

Automation dapat menemukan:

```text
P21.md → PASS
index → REVISE
```

Tetapi automation tidak selalu dapat menentukan mengapa konflik terjadi.

Human review diperlukan untuk menentukan:

- source mana yang authoritative;
- apakah derived view stale;
- apakah source sendiri perlu revisi;
- apakah ada perubahan semantik yang belum didokumentasikan.

---

## 29. Prinsip Source of Truth V2

### Prinsip 1 — Authority per concern

Setiap jenis informasi memiliki authoritative source yang jelas.

### Prinsip 2 — Probe owns inquiry

Isi inquiry berasal dari dokumen Probe yang bersangkutan.

### Prinsip 3 — Derived views are not competing sources

Index, graph, dan summary tidak boleh menjadi semantic authority kedua tanpa keputusan eksplisit.

### Prinsip 4 — README owns repository orientation

README menjadi sumber untuk purpose, scope, dan rules pada namespace yang diwakilinya.

### Prinsip 5 — Schema owns metadata rules

Aturan metadata berasal dari schema yang berlaku.

### Prinsip 6 — Git owns history

Sejarah perubahan repository dirujuk melalui Git.

### Prinsip 7 — Timestamp does not determine authority

Yang terakhir diedit tidak otomatis paling benar.

### Prinsip 8 — Summary is not source

Ringkasan boleh ada, tetapi tidak menggantikan reasoning source.

### Prinsip 9 — Conflict must be resolvable

Setiap konflik harus dapat ditelusuri ke authoritative source.

### Prinsip 10 — Automation detects, humans resolve semantics

Automation membantu menemukan drift; manusia menentukan penyelesaian semantic conflict.

---

## 30. Model Authority Repository

```text
                    REPOSITORY
                        │
        ┌───────────────┼────────────────┐
        ↓               ↓                ↓
    Governance        Probe           Schema
        │               │                │
        ↓               ↓                ↓
     rules          inquiry          metadata rules
        │               │                │
        └───────────────┼────────────────┘
                        ↓
                 Derived Views
              ┌─────────┼─────────┐
              ↓         ↓         ↓
            Index     Graph    Summary
```

Derived views mengambil informasi dari source yang sesuai, bukan bersaing dengannya.

---

## 31. Batas P21

P21 belum menetapkan:

- satu file authority registry final;
- tooling source-of-truth checker;
- format manifest metadata;
- aturan generated-file marker final;
- seluruh hierarchy dokumentasi governance.

P21 menetapkan prinsip arsitektural bahwa **authority harus ditentukan per concern, bukan dengan menunjuk satu artefak sebagai sumber untuk seluruh repository.**

---

# Decision

**PASS — SOURCE OF TRUTH DITENTUKAN PER CONCERN DAN DERIVED VIEW TIDAK BOLEH MENJADI SUMBER KEDUA YANG BERSAING**

Keputusan P21:

> **Repository V2 harus memiliki authoritative source yang jelas untuk setiap jenis informasi. Isi inquiry berasal dari Probe yang bersangkutan; aturan repository berasal dari dokumen governance/README yang sesuai; aturan metadata berasal dari schema; sejarah perubahan berasal dari Git; sedangkan index, graph, dan summary berfungsi sebagai derived/navigation views. Jika terjadi konflik, authority ditentukan berdasarkan concern, bukan berdasarkan file yang terakhir diedit.**

Dengan keputusan ini, repository dapat memiliki banyak representasi informasi tanpa berubah menjadi kumpulan sumber kebenaran yang saling bersaing.
