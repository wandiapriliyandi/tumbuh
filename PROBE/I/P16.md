# P16 — Bagaimana Perubahan Schema dan Struktur Repository Dikelola tanpa Merusak Lineage Probe?

## Tujuan

Menetapkan prinsip pengelolaan perubahan schema metadata dan struktur repository agar evolusi arsitektur V2 tetap memungkinkan tanpa menghilangkan identity, lineage, history, dan traceability Probe yang sudah ada.

---

## 1. Titik Berangkat

P0 menetapkan V2 sebagai ruang evolusi arsitektur.

P8 menetapkan bahwa P-number adalah identity yang stabil.

P10–P11 menetapkan bahwa lifecycle dan decision memiliki makna yang berbeda dari identity.

P12 menetapkan bahwa metadata dapat distandarkan dan schema dapat berkembang.

P13 menetapkan bahwa lineage bergantung pada identity, bukan sekadar lokasi file.

P14–P15 menetapkan bahwa index dan derived view harus dapat mengikuti perubahan source tanpa menjadi sumber kebenaran kedua.

Maka muncul pertanyaan:

> **Jika struktur repository atau schema metadata perlu berubah, bagaimana perubahan tersebut dilakukan tanpa memutus identity dan lineage Probe yang telah ada?**

---

## 2. Evolusi Struktur Tidak Sama dengan Penghapusan Sejarah

Repository V2 memang dibuat untuk memungkinkan evolusi.

Namun evolusi tidak boleh berarti:

```text
struktur baru
↓
hapus struktur lama
↓
hilang konteks
```

Model yang lebih aman:

```text
struktur lama
↓
perubahan terencana
↓
struktur baru
↓
identity dan lineage tetap dapat ditelusuri
```

Perubahan arsitektur harus menjaga **continuity of identity**, meskipun lokasi atau representasi dapat berubah.

---

## 3. Identity Lebih Stabil daripada Path

P13 sudah menetapkan prinsip bahwa relation sebaiknya mengacu pada P-number, bukan path.

Contoh:

```text
P14
```

adalah identity.

Sedangkan:

```text
PROBE/I/P14.md
```

adalah lokasi saat ini.

Jika repository berubah menjadi:

```text
PROBE/I/archive/P14.md
```

identity P14 tidak berubah.

Dengan demikian restrukturisasi folder tidak otomatis merusak lineage.

---

## 4. Schema Juga Merupakan Artefak yang Dapat Berevolusi

Schema metadata bukan sesuatu yang harus dianggap final selamanya.

Contoh konseptual:

```text
Schema V1
P-number
Title
Lifecycle
Decision
```

kemudian berkembang menjadi:

```text
Schema V2
P-number
Title
Lifecycle
Decision
Relations
```

Perubahan tersebut adalah perubahan **repository architecture**, bukan perubahan identity Probe.

Karena itu schema sendiri harus memiliki history perubahan yang dapat ditelusuri.

---

## 5. Jangan Mengubah Identity demi Menyesuaikan Schema

Jika schema berubah, jangan melakukan:

```text
P14 → Q07
```

hanya karena naming convention baru.

Jika ada kebutuhan mengganti representasi identity, hubungan antara identifier lama dan baru harus dikelola secara eksplisit.

Namun prinsip default tetap:

> **Identity yang sudah digunakan tidak diubah hanya karena schema berubah.**

Hal ini mempertahankan aturan P8.

---

## 6. Structural Migration

Jika struktur repository perlu diubah, gunakan konsep **migration**.

Secara konseptual:

```text
Current structure
      ↓
Migration rule
      ↓
New structure
      ↓
Validation
      ↓
Lineage preserved
```

Migration harus dapat menjawab:

- apa yang berubah;
- mengapa berubah;
- artefak mana yang terdampak;
- identity apa yang tetap;
- relation apa yang harus diperiksa;
- derived view apa yang perlu dibangun ulang.

---

## 7. Rename Tidak Sama dengan New Probe

Perubahan judul atau nama file tidak otomatis menghasilkan Probe baru.

Contoh:

```text
P14 — Title Lama
       ↓
P14 — Title Baru
```

tetap P14 jika unit inquiry sama.

Demikian juga:

```text
P14.md
↓
P14-metadata.md
```

tidak otomatis menjadi P baru.

Identity mengikuti unit inquiry, bukan nama file.

---

## 8. Move Tidak Sama dengan New Probe

Memindahkan file:

```text
PROBE/I/P14.md
↓
PROBE/I/archive/P14.md
```

adalah perubahan lokasi.

Bukan:

```text
P14 → P15
```

dan bukan pembentukan inquiry baru.

History Git dapat mencatat perpindahan tersebut, sementara P-number tetap menjadi identity.

---

## 9. Schema Migration Harus Memisahkan Data Lama dan Aturan Baru

Jika field baru diperkenalkan, jangan langsung menganggap semua Probe lama sudah memiliki informasi tersebut.

Misalnya:

```text
Schema lama → tidak memiliki Relations
Schema baru → Relations tersedia
```

Maka ada beberapa kemungkinan:

```text
existing metadata
→ migrated
```

atau:

```text
existing metadata
→ tetap valid dengan field optional
```

Pilihan tersebut harus ditentukan oleh schema migration, bukan diimprovisasi per Probe.

---

## 10. Backward Compatibility

Perubahan schema idealnya mempertimbangkan kemampuan repository untuk tetap membaca artefak lama.

Prinsipnya:

> **Selama memungkinkan, perubahan baru sebaiknya tidak membuat dokumentasi lama kehilangan makna atau tidak dapat dipetakan.**

Backward compatibility tidak berarti schema tidak boleh berubah.

Artinya perubahan harus mempertimbangkan konsekuensi terhadap history yang sudah ada.

---

## 11. Tidak Semua Perubahan Membutuhkan Migrasi Besar

Perubahan dapat memiliki skala berbeda.

### Editorial

```text
typo
formatting
link
```

→ tidak membutuhkan schema migration.

### Metadata extension

```text
field baru
```

→ mungkin membutuhkan migration ringan.

### Schema change

```text
field diubah maknanya
vocabulary berubah
```

→ membutuhkan compatibility review.

### Structural change

```text
folder dipindah
namespace diubah
```

→ membutuhkan repository migration.

### Identity change

```text
P-number diubah
```

→ harus dianggap high-risk dan pada prinsipnya dihindari.

---

## 12. Perubahan Makna Field Lebih Berbahaya daripada Penambahan Field

Misalnya:

```text
Lifecycle
```

awalnya berarti kondisi dokumentasi.

Kemudian digunakan untuk berarti kualitas inquiry.

Ini bukan sekadar perubahan schema teknis.

Ini adalah perubahan semantik.

Karena itu perubahan yang mengubah **makna field** harus diperlakukan lebih hati-hati daripada penambahan field baru.

---

## 13. Vocabulary Migration

P11 menetapkan vocabulary lifecycle.

Jika suatu saat vocabulary perlu berubah, misalnya:

```text
ACTIVE → INQUIRY
```

maka migration harus mendefinisikan apakah:

```text
ACTIVE = INQUIRY
```

atau keduanya memiliki makna berbeda.

Jangan melakukan search-and-replace tanpa memeriksa semantic equivalence.

---

## 14. Decision History Harus Dipertahankan

Perubahan schema tidak boleh menghapus decision historis hanya karena format baru berbeda.

Contoh:

```text
Decision: PASS
```

Jika schema baru menggunakan struktur berbeda, informasi bahwa Probe pernah memperoleh decision PASS harus tetap dapat ditelusuri.

Perubahan representasi ≠ penghapusan sejarah.

---

## 15. Lineage Harus Diverifikasi Setelah Migration

Setelah structural atau schema migration, pemeriksaan penting adalah:

```text
Apakah P-number tetap unik?
Apakah semua target relation masih ditemukan?
Apakah archived Probe masih dapat ditelusuri?
Apakah index masih menunjuk ke lokasi yang benar?
Apakah metadata masih memiliki makna yang sama?
```

Migration dianggap berhasil bukan hanya ketika file berhasil dipindahkan, tetapi ketika **traceability tetap utuh**.

---

## 16. Derived View Harus Dibangun Ulang

Karena P14–P15 menetapkan index sebagai derived view, perubahan struktur tidak seharusnya diselesaikan dengan mengedit semua view secara manual tanpa sumber yang jelas.

Modelnya:

```text
Migration
   ↓
Source updated
   ↓
Validation
   ↓
Derived views rebuilt
```

Dengan demikian index mengikuti repository baru dari source yang telah dimigrasikan.

---

## 17. Migration Harus Memiliki Checkpoint

Perubahan besar sebaiknya tidak dilakukan sebagai satu operasi yang tidak dapat diperiksa.

Secara konseptual:

```text
Before
↓
Migration preparation
↓
Migration
↓
Validation
↓
Commit
↓
After
```

Setiap tahap perlu meninggalkan history yang cukup untuk memahami perubahan.

Ini sesuai dengan fungsi Git sebagai historical record.

---

## 18. Reversibility

Tidak semua migration harus dapat dibatalkan secara otomatis.

Namun perubahan berisiko tinggi sebaiknya dirancang agar dapat dipulihkan melalui:

- Git history;
- commit sebelum migration;
- mapping identifier;
- migration notes;
- derived-view regeneration.

Prinsipnya:

> **Jika perubahan tidak dapat dibuat reversible secara teknis, setidaknya reasoning dan state sebelum perubahan harus tetap recoverable.**

---

## 19. Migration Log

Untuk perubahan yang berdampak luas, dapat digunakan dokumentasi migration sederhana:

```text
Migration ID
Date
Reason
Affected scope
Old schema/structure
New schema/structure
Compatibility notes
Validation result
```

P16 belum menentukan format file migration tersebut.

Yang ditetapkan adalah kebutuhan akan traceability untuk perubahan arsitektur repository yang signifikan.

---

## 20. Governance untuk Schema Change

Perubahan schema sebaiknya melalui pertanyaan minimum:

```text
Apa masalah yang ingin diselesaikan?
Apa yang berubah?
Apakah makna field berubah?
Apa dampaknya terhadap Probe lama?
Apakah lineage tetap valid?
Apakah index dapat dibangun ulang?
Apakah migration dapat diverifikasi?
```

Ini merupakan governance terhadap **repository architecture**, bukan penilaian terhadap isi inquiry.

---

## 21. Human dan Machine

Seperti P9, P12, dan P15:

```text
Human
→ menentukan kebutuhan dan makna perubahan

Machine
→ menjalankan / memeriksa perubahan struktural
```

Machine dapat mendeteksi:

```text
duplicate identity
broken references
missing fields
invalid schema
stale index
```

Tetapi machine tidak boleh menentukan sendiri bahwa perubahan schema aman secara semantik.

---

## 22. High-Risk Changes

Beberapa perubahan perlu diperlakukan sebagai high-risk:

```text
mengubah P-number
mengubah makna lifecycle
mengubah makna decision
menghapus relation history
menghapus archived Probe
mengganti namespace tanpa mapping
```

Perubahan tersebut berpotensi memutus lineage dan harus mendapat scrutiny lebih tinggi.

---

## 23. Prinsip Evolusi Schema dan Struktur

### Prinsip 1 — Identity first

P-number tidak dikorbankan demi kerapian schema.

### Prinsip 2 — Path is replaceable

Lokasi file dapat berubah selama identity dan relation tetap dapat ditelusuri.

### Prinsip 3 — Schema is versionable

Schema boleh berevolusi dan history perubahan harus dapat dilacak.

### Prinsip 4 — Semantics matter

Perubahan makna field lebih berisiko daripada perubahan sintaks.

### Prinsip 5 — Migration must be traceable

Perubahan besar harus memiliki alasan, scope, dan hasil validasi yang dapat ditelusuri.

### Prinsip 6 — Derived views are rebuildable

Index dan view tidak boleh menghambat restrukturisasi.

### Prinsip 7 — History is preserved

Perubahan representasi tidak boleh menghapus sejarah.

### Prinsip 8 — Compatibility is considered

Dokumentasi lama harus tetap dapat dipahami atau dipetakan sejauh memungkinkan.

### Prinsip 9 — High-risk changes need stronger review

Governance mengikuti dampak perubahan.

### Prinsip 10 — Automation validates, humans judge

Tooling membantu migrasi, tetapi makna perubahan tetap membutuhkan judgment manusia.

---

## 24. Model Evolusi

Secara konseptual:

```text
             CURRENT REPOSITORY
                    │
                    ↓
              CHANGE PROPOSAL
                    │
                    ↓
              IMPACT REVIEW
                    │
              ┌─────┴─────┐
              ↓           ↓
           Schema      Structure
           Change       Change
              │           │
              └─────┬─────┘
                    ↓
                 MIGRATE
                    ↓
                VALIDATE
                    ↓
          ┌─────────┴─────────┐
          ↓                   ↓
      Source valid       Lineage valid
          │                   │
          └─────────┬─────────┘
                    ↓
             REBUILD VIEWS
                    ↓
              NEW STATE
```

Model ini memungkinkan V2 berevolusi tanpa menganggap setiap perubahan sebagai reset.

---

## 25. Batas P16

P16 belum menetapkan:

- format versioning schema final;
- migration tooling tertentu;
- aturan semver untuk metadata schema;
- format migration log;
- mekanisme rollback otomatis;
- CI pipeline tertentu.

P16 menetapkan prinsip arsitektural bahwa **schema dan struktur repository boleh berevolusi, tetapi identity, lineage, history, dan semantic continuity harus dijaga secara eksplisit.**

Pertanyaan berikutnya dapat menguji bagaimana **versi schema, versi repository, dan identity Probe dibedakan** agar tidak terjadi pencampuran antara versioning dengan numbering P.

---

# Decision

**PASS — SCHEMA DAN STRUKTUR BOLEH BEREVOLUSI, IDENTITY DAN LINEAGE HARUS TETAP TRACEABLE**

Keputusan P16:

> **Perubahan schema maupun struktur repository harus diperlakukan sebagai evolusi yang dapat dilacak, bukan sebagai reset. P-number tetap menjadi identity, path dapat berubah, schema dapat berkembang, dan derived views dapat dibangun ulang. Migration harus mempertimbangkan compatibility, memeriksa dampak semantik, memvalidasi lineage, serta mempertahankan history agar perubahan arsitektur V2 tidak memutus intellectual lineage yang telah terbentuk.**
