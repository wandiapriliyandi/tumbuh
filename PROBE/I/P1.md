# P1 — Mengapa Struktur Repository V2 Dipisahkan Berdasarkan Fungsi?

## Tujuan

Menjelaskan alasan konseptual di balik pemisahan struktur repository TUMBUH V2 berdasarkan **fungsi**, bukan semata-mata berdasarkan urutan pembuatan dokumen atau kronologi pekerjaan.

Kajian ini berada pada ranah **arsitektur repository dan organisasi pengetahuan TUMBUH**.

P1 tidak membahas isi atau kebenaran substantif dari Foundation, Core Model, Progression, Assessment, Intervention, Implementation, Programs, Research, atau domain lainnya. Yang dibahas adalah **mengapa ruang-ruang tersebut dipisahkan secara arsitektural**.

---

# 1. Titik Berangkat

P0 menetapkan bahwa V2 diperlukan karena perkembangan TUMBUH tidak lagi hanya berupa penambahan konten, tetapi juga mencakup restrukturisasi cara pengetahuan diorganisasikan.

Konsekuensinya, repository V2 tidak ideal jika diperlakukan sebagai satu kumpulan dokumen besar.

Repository perlu menjawab pertanyaan sederhana:

> **Dokumen ini memiliki fungsi apa dalam keseluruhan sistem?**

Dari sini muncul prinsip utama P1:

> **Struktur repository V2 disusun berdasarkan fungsi pengetahuan dan fungsi kerja, bukan berdasarkan urutan dokumen dibuat.**

---

# 2. Masalah Jika Semua Dokumen Dicampur

Bayangkan seluruh artefak TUMBUH diletakkan dalam satu ruang:

```text
TUMBUH/
├── dokumen A
├── dokumen B
├── dokumen C
├── penelitian X
├── konsep Y
├── SOP Z
├── draft lama
└── ...
```

Pada awal pengembangan, struktur seperti ini mungkin masih dapat digunakan.

Tetapi ketika repository berkembang, muncul beberapa masalah:

- fungsi dokumen menjadi tidak jelas;
- hubungan antarartefak sulit dipahami;
- dokumen riset bercampur dengan hasil sistem;
- artefak operasional bercampur dengan keputusan konseptual;
- arsip bercampur dengan materi aktif;
- perubahan struktur menjadi semakin sulit dilakukan.

Masalah utamanya bukan jumlah file.

Masalah utamanya adalah:

> **tidak adanya batas fungsi yang jelas.**

---

# 3. Repository Bukan Gudang File

Dalam V2, repository tidak dipandang hanya sebagai tempat menyimpan file.

Repository berfungsi sebagai:

```text
ruang pengetahuan
      +
ruang pengembangan
      +
ruang dokumentasi
      +
ruang pelacakan perubahan
```

Karena itu struktur folder harus membawa informasi tentang **peran sebuah artefak**.

Folder bukan sekadar alamat file.

Folder menjadi bagian dari metadata konseptual repository.

Ketika sebuah dokumen ditempatkan dalam ruang tertentu, pembaca seharusnya dapat memperoleh petunjuk:

> dokumen ini dibuat untuk fungsi apa?

---

# 4. Mengapa Berdasarkan Fungsi?

Pemisahan berdasarkan fungsi memberikan beberapa keuntungan.

### 4.1 Batas menjadi jelas

Setiap ruang memiliki tujuan yang lebih terdefinisi.

### 4.2 Navigasi menjadi lebih mudah

Pengguna tidak perlu mengetahui sejarah pembuatan setiap file untuk menemukan artefak yang dibutuhkan.

### 4.3 Perubahan lebih terkontrol

Perubahan pada satu fungsi tidak otomatis berarti perubahan pada seluruh repository.

### 4.4 Pengetahuan lebih mudah dipelihara

Artefak dengan karakter yang berbeda dapat dikelola menggunakan aturan yang berbeda.

### 4.5 Evolusi dapat dilacak

Perubahan fungsi dapat terlihat melalui perubahan struktur maupun isi.

---

# 5. Contoh Struktur V2

Pada `v2.0.0`, repository telah menggunakan pemisahan ruang seperti:

```text
01_FOUNDATION
02_CORE_MODEL
03_PROGRESSION
04_ASSESSMENT
05_INTERVENTION
06_IMPLEMENTATION
07_PROGRAMS
08_SOURCES_AND_EVIDENCE
09_RESEARCH
99_ARCHIVE
```

Struktur ini menunjukkan sebuah prinsip:

> **bagian-bagian repository memiliki fungsi yang berbeda sehingga tidak harus hidup dalam ruang yang sama.**

Perlu ditekankan bahwa P1 belum menilai apakah setiap nama folder tersebut merupakan bentuk final.

Yang diuji di sini adalah **prinsip pemisahan berdasarkan fungsi**.

---

# 6. Fungsi Berbeda Membutuhkan Perlakuan Berbeda

Sebuah hasil penelitian dan sebuah prosedur operasional, misalnya, sama-sama merupakan dokumen.

Tetapi keduanya tidak memiliki fungsi yang sama.

```text
Research
   ↓
menyelidiki / menguji / menghasilkan temuan

Implementation
   ↓
mengoperasionalkan sistem
```

Jika keduanya dicampur tanpa batas, pembaca dapat kehilangan konteks.

Karena itu:

> **kesamaan format file tidak berarti kesamaan fungsi.**

Ini merupakan salah satu alasan utama mengapa repository perlu memiliki arsitektur.

---

# 7. Fungsi Lebih Stabil daripada Kronologi

Kronologi menjawab:

> “mana yang dibuat lebih dulu?”

Fungsi menjawab:

> “dokumen ini digunakan untuk apa?”

Untuk repository jangka panjang, pertanyaan kedua biasanya lebih berguna untuk navigasi dan pemeliharaan.

Urutan pembuatan dapat berubah.

Fungsi dapat tetap menjadi identitas utama sebuah ruang.

Maka V2 memilih prinsip:

```text
chronology
   ↓
secondary information

function
   ↓
primary organizational principle
```

Ini bukan berarti kronologi tidak penting.

Kronologi tetap diperlukan untuk lineage dan sejarah, tetapi tidak harus menjadi struktur utama seluruh repository.

---

# 8. Pemisahan Bukan Berarti Isolasi

Ada risiko lain.

Jika folder dipisahkan terlalu ketat, repository dapat berubah menjadi kumpulan silo.

Itu juga tidak diinginkan.

Maka:

```text
separation ≠ isolation
```

Pemisahan berfungsi memberikan batas.

Relasi antarbagian tetap harus dapat ditelusuri.

Secara konseptual:

```text
Function A
    ↕
Function B
    ↕
Function C
```

Jadi arsitektur repository harus memiliki dua kualitas sekaligus:

1. **separation** — batas fungsi jelas;
2. **traceability** — hubungan antarbagian tetap dapat ditelusuri.

---

# 9. Mengapa Ada `99_ARCHIVE`?

Keberadaan ruang archive menunjukkan prinsip yang sama.

Artefak lama tidak selalu harus dihapus hanya karena tidak lagi menjadi bagian dari struktur aktif.

Namun artefak lama juga tidak seharusnya terus bercampur dengan artefak aktif.

Maka:

```text
active knowledge
       │
       │
       ├── current structure
       │
       └── historical material
                    ↓
                 ARCHIVE
```

Archive menjaga sejarah tanpa membuat sejarah mengganggu navigasi struktur aktif.

Ini konsisten dengan prinsip P0 tentang menjaga **lineage** sekaligus memungkinkan **evolution**.

---

# 10. Mengapa `09_RESEARCH` Berbeda dari Ruang Sistem?

Pada level arsitektur repository, research dan system output memiliki fungsi yang berbeda.

Research dapat berisi:

- pertanyaan;
- eksplorasi;
- pengujian;
- kritik;
- temuan;
- alternatif;
- hal-hal yang belum final.

Sementara ruang sistem berisi artefak yang telah diposisikan untuk fungsi tertentu dalam struktur TUMBUH.

Karena karakter epistemiknya berbeda, keduanya membutuhkan ruang yang berbeda.

P1 tidak menentukan isi atau metodologi research tersebut.

P1 hanya menetapkan:

> **research perlu memiliki boundary yang dapat dibedakan dari artefak sistem.**

---

# 11. Mengapa `08_SOURCES_AND_EVIDENCE` Dipisahkan?

Hal yang sama berlaku untuk sumber dan evidence.

Sumber yang digunakan untuk membangun atau mendukung sebuah artefak tidak identik dengan artefak itu sendiri.

Secara arsitektural:

```text
Source / Evidence
        ↓
 mendukung / menginformasikan
        ↓
System Artifact
```

Jika keduanya selalu ditempatkan dalam ruang yang sama, perbedaan antara:

> **apa yang menjadi sumber**

dan:

> **apa yang menjadi hasil konstruksi TUMBUH**

menjadi kurang jelas.

Karena itu pemisahan ruang juga membantu menjaga keterlacakan intelektual.

---

# 12. Repository Harus Bisa Dibaca Tanpa Penjelasan Lisan

Salah satu pengujian penting untuk struktur V2 adalah:

> **Apakah orang lain dapat memahami arsitektur repository tanpa harus selalu bertanya kepada pembuatnya?**

Jika jawabannya tidak, maka struktur repository masih terlalu bergantung pada tacit knowledge.

Struktur yang baik harus membawa sebagian konteksnya sendiri.

Dengan demikian:

```text
good repository architecture
          ↓
self-explanatory structure
```

Bukan berarti seluruh makna harus dimasukkan ke dalam nama folder.

Tetapi pembagian ruang harus cukup jelas untuk memberikan orientasi awal.

---

# 13. Prinsip P1

Dari pembahasan ini dapat dirumuskan prinsip:

> **Repository V2 harus mengorganisasikan artefak berdasarkan fungsi utamanya, dengan batas yang cukup jelas untuk menjaga konteks, tetapi dengan keterhubungan yang cukup kuat untuk menjaga traceability.**

Secara ringkas:

```text
Repository Architecture
        │
        ├── Function-based
        ├── Clear boundaries
        ├── Traceable relations
        ├── Historical separation
        └── Long-term maintainability
```

---

# 14. Batas Kajian P1

P1 belum membahas secara rinci:

- mengapa `PROBE` diperlukan;
- mengapa `PROBE` ditempatkan di luar urutan folder utama;
- mengapa ada `PROBE/I`;
- apa arti `I`;
- mengapa dokumentasi P0–Pn menggunakan pola tersebut;
- aturan penamaan folder dan file;
- hubungan branch dengan tag/release;
- aturan lifecycle sebuah artefak.

Pertanyaan tersebut menjadi kajian berikutnya.

---

# 15. Decision

### **PASS — FUNCTION-BASED REPOSITORY ARCHITECTURE**

Kesimpulan P1:

> **Struktur repository V2 perlu dipisahkan berdasarkan fungsi karena repository TUMBUH bukan sekadar kumpulan file, melainkan ruang pengetahuan dan pengembangan yang memiliki jenis artefak dengan fungsi berbeda. Pemisahan berdasarkan fungsi menjaga batas konteks, mempermudah navigasi, mengendalikan perubahan, mempertahankan lineage, dan mendukung pemeliharaan jangka panjang.**

Prinsip ini menjadi dasar untuk menguji pertanyaan berikutnya:

> **Jika repository V2 sudah dipisahkan berdasarkan fungsi, mengapa masih diperlukan ruang khusus bernama `PROBE`?**

**Lanjut → P2 | Mengapa TUMBUH Membutuhkan PROBE?**
