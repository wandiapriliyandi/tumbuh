# P14 — Bagaimana Index dan Peta Probe Dibangun tanpa Menduplikasi Isi Probe?

## Tujuan

Menentukan fungsi index dan peta Probe di dalam repository agar rangkaian P0–Pn mudah dinavigasi dan lineage mudah dipahami, tanpa menjadikan README atau index sebagai salinan isi setiap Probe.

---

## 1. Titik Berangkat

P4 menetapkan bahwa setiap Probe merupakan unit dokumentasi tersendiri.

P6–P8 menetapkan bahwa P-number adalah identity yang stabil dan berfungsi sebagai identifier dokumenter.

P12 menetapkan metadata minimum untuk membantu discovery dan governance.

P13 menetapkan bahwa hubungan antar-Probe membentuk lineage yang dapat dipahami sebagai graph.

Maka muncul persoalan praktis:

> **Jika Probe tersebar dalam banyak file dan hubungan antar-Probe dapat membentuk graph, bagaimana pembaca menemukan dan memahami keseluruhannya tanpa membuat satu file index menjadi duplikasi isi seluruh Probe?**

---

## 2. Index Bukan Repository Kedua

Index seharusnya menjadi **peta**, bukan salinan repository.

Perbedaannya:

```text
Probe file
→ menyimpan inquiry

Index
→ menunjukkan lokasi dan metadata ringkas

Lineage map
→ menunjukkan hubungan antar-Probe
```

Jika index mengulang seluruh isi Probe, akan muncul dua sumber informasi yang harus dipelihara secara bersamaan.

Itu meningkatkan risiko drift dan inkonsistensi.

---

## 3. Fungsi Utama Index

Index memiliki fungsi navigasi dan discovery.

Pembaca seharusnya dapat menjawab dengan cepat:

- Probe apa saja yang tersedia?
- P-number berapa yang ada?
- Apa judul/fokus singkatnya?
- Status lifecycle-nya apa?
- Decision-nya apa jika sudah ada?
- Probe tersebut berhubungan dengan mana?
- Di mana file aslinya?

Index tidak perlu menjawab seluruh pertanyaan inquiry.

Untuk itu pembaca diarahkan ke file Probe.

---

## 4. Single Source of Truth

Prinsip penting:

> **Isi inquiry tetap memiliki satu sumber utama: file Probe itu sendiri.**

Contoh:

```text
P14.md
  ↓
isi inquiry + metadata utama
```

Sedangkan:

```text
README.md
  ↓
index / navigation
```

README tidak menjadi tempat kedua untuk menyimpan keseluruhan reasoning P14.

Jika title atau status berubah, index seharusnya dapat diperbarui berdasarkan metadata yang sama, bukan melalui penyalinan manual isi inquiry.

---

## 5. Index Minimum

Index minimum dapat berbentuk tabel sederhana:

| P | Title | Lifecycle | Decision | Relations |
|---|---|---|---|---|
| P0 | ... | DECIDED | PASS | — |
| P1 | ... | DECIDED | PASS | P0 |
| P2 | ... | DECIDED | PASS | P1 |

Kolom tersebut adalah contoh konseptual.

Yang penting index hanya menyimpan **ringkasan navigasional**, bukan seluruh isi Probe.

---

## 6. Index dan P-number

P-number adalah kunci utama index.

Contoh:

```text
P0
P1
P2
...
P14
```

Karena identifier stabil, index dapat menggunakannya sebagai anchor.

Jika title berubah:

```text
P14 tetap P14
```

Index hanya perlu memperbarui representasi title jika diperlukan.

Identity tidak berubah.

---

## 7. Index dan Lifecycle

Index dapat memperlihatkan lifecycle agar pembaca mengetahui kondisi Probe tanpa harus membuka seluruh file.

Contoh:

```text
P8  | DECIDED  | PASS
P9  | ARCHIVED | PASS
P10 | DECIDED  | PASS
P11 | DECIDED  | PASS
P12 | DECIDED  | PASS
P13 | ACTIVE   | —
```

Namun index tidak boleh mengubah status menjadi penilaian kualitas.

`ARCHIVED` bukan berarti “buruk”.

---

## 8. Index dan Decision

Decision dapat ditampilkan secara ringkas jika tersedia.

Contoh:

```text
P8  → DECIDED / PASS
P9  → DECIDED / REVISE
P10 → ACTIVE / —
```

Jika belum ada decision, jangan mengarang nilai.

Index harus merepresentasikan metadata sumber, bukan melakukan interpretasi baru.

---

## 9. Index dan Lineage

Index dapat menunjukkan hubungan secara ringkas:

```text
P13 → FOLLOW_UP → P8
P14 → DERIVED_FROM → P11
```

Namun graph lengkap tidak harus dipaksakan ke dalam tabel.

Untuk hubungan kompleks, index dapat menyediakan tautan ke Probe terkait atau peta lineage terpisah.

---

## 10. Linear Index dan Graph Map

Ada dua kebutuhan berbeda:

### Linear index

Memudahkan navigasi berdasarkan P-number.

```text
P0
P1
P2
P3
...
P14
```

### Graph map

Memudahkan pemahaman hubungan:

```text
       P2
      /  \
    P5    P7
      \  /
       P9
```

Keduanya tidak perlu digabung menjadi satu artefak besar.

Prinsipnya:

> **Index menjawab “di mana dan apa?”, lineage map menjawab “berhubungan bagaimana?”.**

---

## 11. Jangan Membuat README Terlalu Pintar

README sebaiknya tidak menjadi mesin interpretasi.

README dapat memberikan:

- tujuan folder;
- aturan dokumentasi;
- daftar Probe;
- metadata ringkas;
- tautan navigasi.

README tidak sebaiknya menjadi tempat untuk:

- mengulang reasoning setiap Probe;
- menyimpulkan isi Probe dengan cara baru;
- membuat ranking Probe;
- menjadi sumber decision alternatif.

Jika README mulai menjawab pertanyaan inquiry yang sebenarnya milik P-file, batas repository mulai kabur.

---

## 12. Index Harus Dapat Dibangun Ulang

Idealnya index merupakan artefak yang **rebuildable**.

Secara konseptual:

```text
P0.md
P1.md
P2.md
...
Pn.md
   ↓
metadata extraction
   ↓
index generation
```

Dengan demikian index dapat diperbarui dari sumber utama.

Ini mengurangi risiko:

```text
Probe berkata A
Index berkata B
```

---

## 13. Manual vs Automation

Index dapat dibuat atau diperbarui secara manual pada tahap awal.

Namun struktur metadata P12 membuka peluang automation.

Automation dapat:

```text
scan PROBE/I/
↓
read metadata
↓
validate identity
↓
sort P-number
↓
generate index
```

Dengan begitu index tidak perlu menjadi pekerjaan administratif yang berulang.

---

## 14. Automation Tidak Boleh Mengubah Isi

Generator index seharusnya hanya mengambil data yang sudah tersedia.

Misalnya:

```text
P13.md
Lifecycle: ACTIVE
Decision: null
```

maka index menampilkan informasi tersebut.

Generator tidak boleh menyimpulkan:

```text
ACTIVE → berarti belum selesai
```

kecuali makna tersebut memang sudah ditetapkan oleh schema.

Index adalah representasi, bukan tempat menghasilkan keputusan baru.

---

## 15. Orphan Probe

Index juga dapat membantu mendeteksi Probe yang tidak terpetakan.

Contoh:

```text
repository:
P0
P1
P2
P3
P14

index:
P0
P1
P2
P3
```

P14 menjadi kandidat **orphan documentation**.

Ini tidak otomatis berarti P14 salah.

Artinya governance perlu memeriksa apakah index belum diperbarui atau Probe memang belum terdaftar.

---

## 16. Broken Reference

Sebaliknya:

```text
P14
Relation: FOLLOW_UP → P99
```

ketika P99 tidak ada, automation dapat menandai broken reference.

Hal ini merupakan masalah struktural repository, bukan alasan untuk mengubah isi inquiry secara otomatis.

---

## 17. Index Tidak Menggantikan File Probe

Seorang pembaca yang ingin mengetahui keseluruhan inquiry tetap harus membuka file P terkait.

Alurnya:

```text
Index
  ↓
pilih P
  ↓
open Probe
  ↓
baca inquiry
  ↓
ikuti relation bila diperlukan
```

Index menjadi pintu masuk, bukan tujuan akhir.

---

## 18. Beberapa Index Dapat Ada

Tidak harus hanya ada satu cara membaca repository.

Secara konseptual dapat terdapat:

```text
Master Index
→ seluruh Probe

Status Index
→ berdasarkan lifecycle

Lineage Map
→ berdasarkan relation

Chronological View
→ berdasarkan perkembangan dokumenter
```

Namun semua view tersebut harus bersumber dari identity dan metadata yang sama.

Jangan membuat beberapa daftar yang memiliki identity berbeda untuk Probe yang sama.

---

## 19. Index Tidak Membuat Taxonomy Baru

Pembuatan index berdasarkan:

```text
status
relation
tanggal
namespace
```

tidak berarti kita sedang membuat klasifikasi teoritis baru atas Probe.

Ini hanya **cara navigasi repository**.

Hal ini konsisten dengan prinsip bahwa pengelompokan dokumentasi tidak otomatis menjadi taxonomy teoritis.

---

## 20. Index dan Roman Namespace

Karena P3 menetapkan bahwa `PROBE/I`, `PROBE/II`, dan seterusnya merupakan grouping dokumenter, index harus mempertahankan konteks namespace.

Contoh konseptual:

```text
PROBE/I/P14
PROBE/II/Pxx
PROBE/III/Pxx
```

P-number perlu dibaca bersama konteks namespace jika repository memungkinkan identifier yang sama muncul pada grouping berbeda.

Index tidak boleh menghapus konteks lokasi hanya demi membuat daftar terlihat sederhana.

---

## 21. Index sebagai Navigation Layer

Arsitektur dokumentasi dapat dipahami sebagai:

```text
                 Repository
                     │
              ┌──────┴──────┐
              │             │
            Index          Probe
              │             │
        discovery       inquiry content
              │             │
              └──────┬──────┘
                     │
                  Lineage
                     │
                  Graph
```

Index berada sebagai **navigation layer**, bukan sebagai substantive inquiry layer.

---

## 22. Prinsip Index dan Peta Probe

### Prinsip 1 — Index adalah peta

Index membantu menemukan dan memahami posisi Probe.

### Prinsip 2 — Probe adalah sumber isi

Isi inquiry tidak diduplikasi ke index.

### Prinsip 3 — Identity menjadi anchor

P-number menjadi kunci navigasi utama.

### Prinsip 4 — Metadata dapat diringkas

Lifecycle, decision, dan relation dapat ditampilkan secara ringkas.

### Prinsip 5 — Lineage dapat divisualisasikan terpisah

Graph tidak harus dipaksakan menjadi tabel.

### Prinsip 6 — Index harus rebuildable

Sedapat mungkin index dapat dibangun dari metadata sumber.

### Prinsip 7 — Satu sumber kebenaran

Index tidak boleh menjadi sumber alternatif untuk isi Probe.

### Prinsip 8 — View boleh banyak, identity tetap satu

Berbagai index boleh ada selama mengacu pada identity dan metadata yang sama.

### Prinsip 9 — Index bukan taxonomy

Pengelompokan navigasi tidak otomatis menjadi klasifikasi teoritis.

### Prinsip 10 — Automation membantu discovery

Machine dapat membangun dan memvalidasi index tanpa mengambil alih judgment inquiry.

---

## 23. Model Minimum yang Direkomendasikan

Untuk PROBE/I, model paling sederhana adalah:

```text
PROBE/I/
│
├── README.md       ← map / navigation
├── P0.md           ← inquiry
├── P1.md           ← inquiry
├── P2.md           ← inquiry
├── ...
└── Pn.md           ← inquiry
```

Kemudian metadata dapat digunakan untuk membangun view tambahan tanpa memindahkan isi inquiry keluar dari file Probe.

---

## 24. Batas P14

P14 menetapkan fungsi index dan peta Probe, tetapi belum menetapkan:

- format teknis index;
- apakah index harus selalu manual atau otomatis;
- schema machine-readable final;
- tool khusus untuk visualisasi graph;
- lokasi pasti setiap jenis index.

P14 hanya menetapkan prinsip arsitektural bahwa **index adalah navigation layer dan Probe file tetap menjadi sumber utama inquiry**.

Pertanyaan berikutnya dapat masuk ke persoalan **bagaimana README dan index dipelihara ketika jumlah Probe terus bertambah tanpa menjadi bottleneck governance**.

---

# Decision

**PASS — INDEX ADALAH NAVIGATION LAYER, BUKAN DUPLIKASI ISI PROBE**

Keputusan P14:

> **Index dan peta Probe harus membantu discovery, navigasi, dan pemahaman lineage tanpa menggandakan isi inquiry. File Probe tetap menjadi sumber utama isi dan identity, sedangkan index menjadi representasi ringkas yang idealnya dapat dibangun kembali dari metadata. Berbagai view boleh tersedia, tetapi semuanya harus menggunakan identity dan metadata yang sama.**
